# ADR 0001: 第一阶段范围与 Runtime 发布

## 状态

Accepted

## 背景

MagicOps 的长期方向包括动态接口、数据运维、系统集成和 Arthas 线上诊断。

如果把所有能力都放进第一阶段，MVP 会过宽，并且在核心平台闭环被验证前模糊安全边界、审批规则和发布控制。

## 决策

第一阶段聚焦三个业务闭环：

1. 动态查询接口；
2. 受控数据修复；
3. HTTP 接口适配。

第一阶段同时建立共享治理与发布路径：

- fork 或导入 magic-api，并建立 MagicOps 单仓库结构；
- 保留在线编辑/调试和动态 API 映射能力；
- 增加认证、权限、操作审计和执行审计；
- 建立草稿、版本、审批、发布、签名和 Runtime 加载生命周期；
- 生产 Runtime 只读，只加载已签名发布包；
- Console 在线推送已签名发布包到 Runtime；
- 平台持有签名私钥；
- Runtime 只持有公钥验签材料；
- SQL Guard、Crypto 和 HTTP 目标管理围绕三个第一阶段闭环建设。

Arthas 线上诊断是核心差异化能力，但属于第二阶段工作。

## 后果

第一阶段验收标准不是“所有模块都存在”，而是“三个高价值闭环可以完成受控发布和执行”。

数据修复和动态 API 共用脚本生命周期，通过场景、风险等级、资源声明、审批策略、SQL Guard 模式和执行审计区分。

在线推送使 Console 到 Runtime 的信任关系成为核心架构边界。发布包必须签名脚本、路由映射、权限、数据源授权、HTTP 目标授权、key reference、策略版本、环境、Runtime 兼容性和发布人身份。

平台持有私钥可以简化第一阶段交付，但要求密钥隔离、权限控制、轮换规划和签名审计。后续版本可以把签名迁移到 KMS、HSM 或独立发布中心。

## 暂缓

- Arthas 诊断中心；
- 多租户；
- 离线发布包作为主发布路径；
- Redis / MQ 完整治理；
- 报表设计器；
- 大规模数据交换；
- 完整 UI 重写。
